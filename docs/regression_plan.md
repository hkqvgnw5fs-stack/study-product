# План регрессионного тестирования

**Продукт:** Система расчёта бонусов сотрудников (Employee Bonus System)
**Версия:** 1.0
**Дата:** 

## 1. Введение

Продукт представляет собой иерархию классов сотрудников (Employee → Manager, Developer, Intern) с расчётом бонусов и полиморфным поведением.

Регрессионное тестирование необходимо для проверки, что после изменений сохраняется:
- Корректность расчёта бонусов (бизнес-логика)
- Полиморфизм (правильный вызов переопределённых методов)
- Стабильность существующих методов (displayInfo, calculateBonus)
- Обработка ошибочных ситуаций

**Почему это важно:** Ошибка в расчёте бонусов может привести к финансовым потерям или недовольству сотрудников. Даже небольшое изменение в базовом классе Employee может сломать поведение всех наследников.

## 2. Границы регрессии

### Входит в регрессию:
- Расчёт бонусов для всех типов сотрудников (Manager, Developer, Intern)
- Метод displayInfo() для всех типов
- Полиморфная диспетчеризация (передача Employee в Company.printEmployeeBonus)
- Основные геттеры/поттеры (если добавятся)
- Обработка граничных значений (salary = 0)
- Устойчивость к null и некорректным данным

### Не входит в регрессию:
- Производительность (циклы > 10000 сотрудников)
- Многопоточность (продукт однопоточный)
- GUI-интерфейс (только консольный вывод)
- Интеграция с внешними базами данных (не предусмотрено)
- Нагрузочное тестирование

## 3. Правила запуска регрессии

Регрессионный прогон обязателен в следующих ситуациях:

| Ситуация | Пример | Почему |
|----------|--------|--------|
| Добавление нового типа сотрудника | Добавили класс Director | Может нарушить существующую иерархию |
| Изменение формулы расчёта бонуса | Поменяли 0.3 на 0.35 | Прямо влияет на бизнес-логику |
| Изменение базового класса Employee | Добавили новое поле | Может сломать всех наследников |
| Исправление дефекта | Починили вывод отрицательного бонуса | Нужно проверить, что ничего не сломалось |
| Обновление JDK | Перешли с 11 на 17 | Может изменить сериализацию |
| Перед каждым релизом | Тестирование перед сдачей | Полная проверка стабильности |

**Регрессия не запускается:**
- При изменении комментариев или форматирования кода
- При добавлении документации
- При локальных экспериментах в отдельной ветке

## 4. Регрессионные сценарии

### Сценарии P1 (Критические — продукт не работает без них)

#### REG-01 | P1 | Расчёт бонуса Manager
- **Цель:** Проверить, что Manager получает 30% от зарплаты
- **Условия:** Создан Manager с salary = 5000.0
- **Шаги:** 
  1. Manager mgr = new Manager("Alice", 5000);
  2. double bonus = mgr.calculateBonus();
- **Ожидаемый результат:** bonus == 1500.0 (5000 * 0.3)
- **Тип:** Автоматизированный (JUnit)
- **Обоснование P1:** Менеджеры — ключевые сотрудники, неверный расчёт бонуса ведёт к финансовым претензиям
 
#### REG-02 | P1 | Расчёт бонуса Developer
- **Цель:** Проверить, что Developer получает 20% от зарплаты
- **Условия:** Создан Developer с salary = 4000.0
- **Шаги:** 
  1. Developer dev = new Developer("Bob", 4000);
  2. double bonus = dev.calculateBonus();
- **Ожидаемый результат:** bonus == 800.0 (4000 * 0.2)
- **Тип:** Автоматизированный
- **Обоснование P1:** Разработчики — основа продукта

#### REG-03 | P1 | Расчёт бонуса Intern
- **Цель:** Проверить, что Intern получает 0% (не получает бонус)
- **Условия:** Создан Intern с salary = 2000.0
- **Шаги:**
  1. Intern intern = new Intern("Charlie", 2000);
  2. double bonus = intern.calculateBonus();
- **Ожидаемый результат:** bonus == 0.0
- **Тип:** Автоматизированный
- **Обоснование P1:** Стажёры не должны получать бонус — это бизнес-правило

#### REG-04 | P1 | Полиморфизм в Company.printEmployeeBonus
- **Цель:** Проверить, что метод правильно обрабатывает всех наследников Employee
- **Условия:** Массив employees содержит Manager, Developer, Intern
- **Шаги:**
  1. Пройти по массиву
  2. Для каждого вызвать Company.printEmployeeBonus(emp)
- **Ожидаемый результат:** Вывод соответствует правильным бонусам (1500, 800, 0)
- **Тип:** Автоматизированный
- **Обоснование P1:** Нарушение полиморфизма сломает всю систему отчётности

#### REG-05 | P1 | Метод displayInfo() для Manager
- **Цель:** Проверить корректный вывод информации о менеджере
- **Условия:** new Manager("Alice", 5000)
- **Шаги:** mgr.displayInfo()
- **Ожидаемый результат:** "Имя: Alice, Зарплата: 5000.0" (формат может отличаться)
- **Тип:** Ручной / Автоматизированный
- **Обоснование P1:** Пользователь должен видеть данные сотрудников

#### REG-06 | P1 | Метод displayInfo() для Developer
- **Цель:** Проверить вывод информации о разработчике
- **Условия:** new Developer("Bob", 4000)
- **Шаги:** dev.displayInfo()
- **Ожидаемый результат:** "Имя: Bob, Зарплата: 4000.0"
- **Тип:** Ручной / Автоматизированный
- **Обоснование P1:** Базовая функция просмотра данных

### Сценарии P2 (Важные — заметно ухудшают работу)

#### REG-07 | P2 | Создание сотрудника с зарплатой 0 (граничное значение)
- **Цель:** Проверить поведение при нулевой зарплате
- **Условия:** new Manager("Zero", 0)
- **Шаги:** mgr.calculateBonus()
- **Ожидаемый результат:** 0.0 (не NaN, не ошибка, не бесконечность)
- **Тип:** Автоматизированный
- **Обоснование P2:** Экстремальное значение, но есть обходной путь

#### REG-08 | P2 | Создание сотрудника с отрицательной зарплатой (ошибочный)
- **Цель:** Проверить, что отрицательная зарплата обрабатывается (или отвергается)
- **Условия:** new Manager("Negative", -1000)
- **Шаги:** Создание объекта → вызов calculateBonus()
- **Ожидаемый результат:** Либо выбрасывается исключение (лучше), либо бонус не рассчитывается некорректно
- **Тип:** Ручной / Автоматизированный (если добавить валидацию)
- **Обоснование P2:** Ошибочные входные данные не должны ломать систему

#### REG-09 | P2 | Создание сотрудника с именем null (ошибочный)
- **Цель:** Проверить обработку null в поле name
- **Условия:** new Developer(null, 3000)
- **Шаги:** dev.displayInfo()
- **Ожидаемый результат:** Не должно быть NullPointerException (либо обработано)
- **Тип:** Ручной
- **Обоснование P2:** Защита от неожиданных null

#### REG-10 | P2 | Создание сотрудника с пустым именем (ошибочный)
- **Цель:** Проверить, пустая строка в имени допустима или нет
- **Условия:** new Intern("", 1500)
- **Шаги:** intern.displayInfo()
- **Ожидаемый результат:** Либо выводится пустое имя, либо ошибка (должно быть определено)
- **Тип:** Ручной
- **Обоснование P2:** Пограничный случай с именем

#### REG-11 | P2 | Очень большая зарплата (переполнение?)
- **Цель:** Проверить работу с большими числами
- **Условия:** new Manager("Rich", 1_000_000_000.0)
- **Шаги:** mgr.calculateBonus()
- **Ожидаемый результат:** 300_000_000.0 (не переполнение, не ошибка)
- **Тип:** Автоматизированный
- **Обоснование P2:** double может обработать, но надо проверить

#### REG-12 | P2 | Метод displayInfo() для Intern
- **Цель:** Проверить вывод информации о стажёре
- **Условия:** new Intern("Charlie", 2000)
- **Шаги:** intern.displayInfo()
- **Ожидаемый результат:** "Имя: Charlie, Зарплата: 2000.0"
- **Тип:** Ручной / Автоматизированный
- **Обоснование P2:** Важно, но не критично

### Сценарии P3 (Дополнительные — удобство)

#### REG-13 | P3 | Форматирование вывода (два знака после запятой)

#### REG-15 | P3 | Проверка, что поле name не изменилось после создания

- **Ожидаемый результат:** Имя осталось "Alice"
- **Тип:** Автоматизированный
- **Обоснование P3:** Проверка контракта неизменяемости (если он есть)

## 6. Связь с автотестами (примеры для будущей реализации)

### REG-01 (P1) — что может случайно сломаться

**Что может пойти не так:**
- Кто-то изменит коэффициент с 0.3 на 0.25 в классе Manager
- Переопределят calculateBonus() и забудут вызвать super()
- Опечатка в формуле (salary * 0.3 написано как salary * 0.03)

**Автотест на JUnit:**
```java
@Test
public void testManagerBonus() {
    Employee mgr = new Manager("Alice", 5000);
    double expected = 1500.0;
    double actual = mgr.calculateBonus();
    assertEquals(expected, actual, 0.01);
}
