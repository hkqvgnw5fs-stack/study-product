1. Введение
Мой продукт  это консольный калькулятор для вычисления гиперболического синуса через ряд Тейлора. Программа принимает от пользователя значение x и точность eps, считает приближение и сравнивает с точной формулой.
План регрессии нужен, потому что даже в таком простом проекте изменения могут сломать старую логику. Например, если я изменю формулу пересчёта члена ряда, могу неправильно считать для отрицательных x. Или если я добавлю новую функцию, могу случайно сломать загрузку данных. Регрессия поможет убедиться, что базовые вещи продолжают работать.

2. Границы регрессии
Входит в регрессию:
вычисление sh(x) для разных значений (положительные, отрицательные, ноль)
работа с разной точностью
обработка ввода пользователя
корректный вывод результатов
работа с файлами (если добавлю сохранение)
Не входит в регрессию:
скорость работы (производительность)
красивый вывод в консоль (форматирование)
редкие экзотические случаи (x > 1000)

3. Правила запуска
Регрессию запускаю обязательно:
после любого изменения в формуле расчёта
перед тем, как показать проект преподавателю
после добавления новой функциональности
после исправления найденного дефекта
перед созданием тега релиза

4. Список регрессионных сценариев
P1  Критические сценарии
REG-01, P1: Вычисление sh(x) для положительного x (например, x=1). Ожидается, что результат ряда близок к формуле (разница меньше eps).
Причина: это основной сценарий, ради которого программа существует.

REG-02, P1: Вычисление sh(x) для отрицательного x (например, x=-1). Ожидается, что результат ряда близок к формуле.
Причина: раньше был дефект с отрицательными числами, это критично.

REG-03, P1: Вычисление sh(0). Ожидается результат 0.
Причина: нулевое значение  важная граница.

REG-04, P1: Сравнение с формулой (math.exp). Ожидается, что разница не больше eps для всех проверяемых x.
Причина: это верификация правильности алгоритма.

REG-05, P1: Программа не падает при вводе нормальных чисел (x=2.5, eps=0.001).
Причина: базовая работоспособность.

REG-06, P1: Количество слагаемых выводится корректно (не ноль, не отрицательное).
Причина: это показатель работы цикла.

P2  Важные сценарии
REG-07, P2: Попытка ввести буквы вместо числа. Ожидается понятное сообщение об ошибке, программа не падает.
Причина: был дефект, пользователь может ошибиться.

REG-08, P2: Ввод eps = 0.0000001 (очень маленькая точность). Ожидается, что программа считает и не зависает.
Причина: проверка граничных условий.

REG-09, P2: Ввод eps = 0.1 (грубая точность). Ожидается быстрый результат с малым числом слагаемых.
Причина: проверка работы с разной точностью.

REG-10, P2: Ввод x = 10. Ожидается, что программа считает (пусть и медленнее).
Причина: проверка больших значений.

REG-11, P2: Ввод x = -10. Ожидается корректный отрицательный результат.
Причина: проверка больших отрицательных значений.

REG-12, P2: Ввод x = 0.5, eps = 0.00001. Ожидается точный результат за разумное число итераций.
Причина: типовой сценарий.

P3  Дополнительные сценарии
REG-13, P3: Вывод сообщения о том, какая точность достигнута.
Причина: удобство пользователя.

REG-14, P3: Проверка, что программа выводит числа с 6 знаками после запятой.
Причина: единообразие вывода.

REG-15, P3: Проверка, что программа пишет "Аналитическая формула: sh(x) = ..." перед расчётом.
Причина: информативность.

6. Связь с автотестами (задание для закрепления)
Сценарий REG-01 (P1): Вычисление sh(1)
Что может случайно сломаться: если я изменю формулу пересчёта члена ряда или начальное значение a, результат станет неправильным.

Простой тест на pytest, который я бы написала:

python
def test_sinh_positive():
    result, _ = sinh_series(1.0, 0.0001)
    expected = (math.exp(1) - math.exp(-1)) / 2
    assert abs(result - expected) < 0.0001
Сценарий REG-07 (P2): Ввод букв вместо числа
Что может случайно сломаться: если я изменю обработку ввода (например, уберу try/except), программа будет падать при вводе букв.

7. Итог
Этот план регрессии поможет мне убедиться, что мой калькулятор работает стабильно после любых изменений. Критические сценарии (P1) я проверяю всегда перед показом проекта. Важные (P2) после исправлений. Дополнительные (P3)  когда есть время. Ошибочные сценарии защищают от глупых падений из-за невнимательного пользователя.
