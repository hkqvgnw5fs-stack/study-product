## 6. Выводы по метрикам

### Вывод 1: Самая проблемная зона — хранение данных

На модуль хранения данных приходится 4 из 10 дефектов (40%). Это говорит о том, что работа с файлами и JSON требует усиления: нужны проверки на повреждённый формат, безопасное восстановление и тесты на граничные случаи.

### Вывод 2: Большинство дефектов связано с вводом и данными

60% дефектов относятся к валидации ввода и работе с файлами. Это указывает на необходимость единого слоя проверки данных и более строгой обработки ошибок.

### Вывод 3: Стабильность воспроизведения высокая

Все 10 дефектов воспроизводятся стабильно. Это упрощает диагностику и ретест, но также говорит о системных проблемах, а не случайных сбоях.

### Вывод 4: Ретест проводится не для всех дефектов

Из 6 закрытых дефектов только 4 прошли ретест. Это означает, что 2 дефекта были закрыты без подтверждения, что повышает риск их возвращения.

### Вывод 5: Критические дефекты открыты

Два дефекта с серьёзностью Critical остаются открытыми. Оба связаны с хранением данных. Это делает релиз рискованным — данные пользователя могут быть потеряны.

## 7. Рекомендации по улучшению

### Рекомендация 1: Усилить модуль хранения данных

Добавить тесты на повреждённый JSON, отсутствие файла и частичную запись. Реализовать безопасное сохранение через временный файл. Это снизит риск потери данных.

### Рекомендация 2: Ввести единый слой валидации

Создать отдельный модуль для проверки пользовательского ввода. Использовать его во всех командах (создание, изменение, поиск). Это исключит повторяющиеся ошибки валидации.

### Рекомендация 3: Сделать ретест обязательным для всех дефектов

Ввести правило: дефект не может быть закрыт без подтверждения ретестом. Это предотвратит возвращение старых багов.

### Рекомендация 4: Добавить обработку исключений

Заменить аварийное завершение программы на вывод диагностического сообщения и переход в безопасный режим там, где это возможно.

### Рекомендация 5: Провести рефакторинг модуля поиска

Упростить логику сравнения строк, добавить нормализацию регистра. Это устранит дефект и сделает код чище.

## 8. Самая проблемная зона проекта

**Наиболее проблемная зона:** Модуль хранения данных (storage.py)

**Почему именно она:**
- 40% всех дефектов сконцентрированы здесь
- Два Critical-дефекта относятся именно к этой зоне
- Ошибки здесь приводят к потере данных пользователя
- Нет безопасного режима при повреждении файла
- Отсутствуют тесты на граничные случаи

**Что нужно сделать:** Усилить обработку ошибок, добавить тесты, реализовать защитное сохранение.

## 9. Итоговое состояние проекта

**Итоговая оценка состояния проекта:**

Проект находится в рабочем, но не полностью стабильном состоянии. Основные пользовательские сценарии реализованы: создание, просмотр, изменение статуса, поиск, сохранение и загрузка данных работают.

**Однако:** модуль хранения данных остаётся зоной риска. Два критических дефекта открыты, и они могут привести к потере данных пользователя. Также требует внимания обработка пользовательского ввода — 3 дефекта связаны с отсутствием валидации.

**До следующего релиза необходимо:**
- Закрыть критический дефект повреждённого JSON
- Закрыть критический дефект потери статуса
- Усилить регрессионные проверки для модуля хранения
- Добавить обработку ошибок ввода

После выполнения этих действий проект можно будет считать стабильным и готовым к демонстрации.

---

## 10. Одна самая важная мера улучшения

**Наиболее важная мера улучшения:**

Добавить безопасное сохранение данных через временный файл и обработку повреждённого JSON с переходом к пустому состоянию.

**Почему это важно:**

Это изменение закроет сразу два Critical-дефекта и предотвратит потерю данных пользователя в будущем. Без этого релиз остаётся рискованным, даже если все остальные дефекты будут исправлены. Также это изменение защитит проект от потери данных при аварийном завершении программы.
